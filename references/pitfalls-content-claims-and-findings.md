# Pitfalls — content, claims, compliance and reporting

Split verbatim out of `dsc-website-qa` SKILL.md so the always-on rules stay readable. Each entry below is the original text in full; read the one you need when its title in the skill's Pitfalls index applies.

- **Check for cross-client contamination on any shared-platform build.** Dealer sites on one platform (the platform, a dealer-CMS, a common template) share code, and a snippet copied between builds carries the *original* client's values — a `linkBackUrl`, a finance API key, a tracking ID, a phone number. Working notes and AI-generated suggestions are the usual carrier: one client's rebuild thread contained a CodeWeavers loader pointing at a *different* dealer's domain with a different `ApiKey`. Grep the live pages for the other client's domain, and read the dealer-specific values in any shared component before reporting on it — then verify whether the live site actually carries the leak or the copy was corrected on the way in, and say which you found. A confirmed leak is Critical: another dealer's identity inside a finance journey is both a compliance and a credibility defect.

- **Feed copy arrives encoded, and both encoding faults publish code instead of characters — loop every VDP, then prove the cause before blaming the dealer's adverts.** Two signatures, often on the same build: double-encoded entities (`&amp;amp;quot;` in the response, so the browser shows `&quot;`) and a stripped Unicode escape (`\u00a3` arriving as `u00a3`, so "£20 a year road tax" prints as "u00a320"). Grep each saved VDP's description for `&amp;(quot|amp|#0?39|gt|lt);|u00[0-9a-f]{2}` and report the **union** of affected cars together with the overlap — 28 entity-hit cars plus 29 escape-hit cars read like two medium findings, but the union was 42 of 62 (68%) and it was the dealer's actual complaint, so the per-signature counts understate it. Then settle *who* broke it with one control-group test: if the unaffected records contain not a single `"`, `&` or `£`, every special character in the estate is encoded and the fault is encode-without-decode in the import pipeline, **not** inconsistent typing by the dealer or wrong data at source. Say which you found — it decides whether the ticket goes to the platform or back to the client, and a dealer who thinks their own adverts are wrong may be leaving over a fixable bug. Method, per-car CSV deliverable and the repair: `references/platform-data-integrity-checks.md` §6.

- **Blank spec fields** (e.g. "Doors:  ") are often a stock feed mapping issue, not a manual data-entry problem — flag to the client's feed provider. **Its mirror case is a null rendered as a value, and a blank-field check scores that clean.** Where the feed has no transmission or fuel for a car, a template that prints the field's fallback string publishes `51,000mi Unlisted 3L Unlisted` beside the price — a blank test passes it because the field is not empty. Grep the rendered page for the template's own null words (`Unlisted`, `N/A`, `Unknown`) inside spec rows and count the affected cars; on one build it hit 6 of 21 VDPs. **Loop the whole stock for both cases rather than spot-checking two VDPs** — a feed-driven null repeats on every car missing that field, and "6 of 21" is a template ticket where "some cars" is a shrug.

- **Yard descriptions are copy-pasted between a dealer's own cars, so read them as data.** The `fulldescription` field is hand-written per vehicle and reused wholesale, which leaves sentences contradicting the car they sit on — a BMW X5 and a Mercedes A180 both describing themselves as a "HIGHLY SPECIFIED **JAPANESE IMPORT**", 8 of 21 listings on one site. This is the client's feed copy rather than a build defect, so it belongs in the client bucket, but it is live, it is wrong, and it undermines the listing. Scan every VDP's description for a small set of contradiction markers — import claims, a different make, another dealer's name, an engine size or powertrain that disagrees with the spec table beside it — and report the count. Check it in the same pass as the spec table, because the two disagreeing is the whole defect.

- **A phone number on the site that belongs to another business is not necessarily contamination — check the dealer's own corporate history first.** A WhatsApp CTA dialling <phone>, a number published on directory listings for "MPO, Oldham", reads as another dealer's number left in a cloned build and is one line from being reported as Critical cross-client contamination. Companies House settled it: the same company (10529262) was incorporated as **Motor Point Oldham Ltd**, renamed to the current trading name in 2025 and still trades as **MPO Car Sales**, so the number is its own legacy line. Search the *company* before the number: a Companies House officer/previous-name list and the FCA register both carry "other names" fields that name the legacy trading style. The finding then changes from "another dealer's number" to a NAP split across four numbers, which is a different severity and a different fix.

- **Grep for Latin filler by its word pattern, never for the literal string `lorem ipsum`.** Demo copy is generated from a word bank, so a live page can carry a whole paragraph of it — `Proin pretium velit at ante pharetra fermentum, Curabitur lorem neque. Proin pretium velit at ante pharetra fermentum. Curabitur lorem neque, aliquam at tristique ac, volutpat sed quam.` — with zero occurrences of `lorem ipsum`, and a presence test on that string reports the page as clean. Match the family (`(?i)lorem|ipsum|dolor sit|consectetur|adipiscing|pretium|pharetra|bibendum|fermentum|vestibulum|tristique`) and print the matched sentence, so the surrounding real words decide it. This is the false negative that matters most on a re-check: "the placeholder is gone" is exactly the verdict a wrong probe returns, and it closes a High finding that is still live.

- **A wrong contact address in a live contact block is High, not a copy nit — the misroute is silent at both ends.** Distinct from demo content: `info@example.com` reads as fake and customers report it, whereas an address belonging to the previous owner, a former employee, the developer or a sibling brand looks entirely correct while sending every enquiry away from the business, so neither the dealer nor the customer ever learns anything broke. Rate it on the *pages it renders on*, not on how small the edit is. When the same wrong detail appears on more than one URL it is in a **shared Theme Builder template** — find and fix the template, not the pages (`references/applying-fixes-via-in-session-rest.md` §"Copy that is not in the page's own data"), and report the page count as the exposure. Check the `href` as well as the label: a `mailto:`/`tel:` whose visible text was updated but whose link was not is still live and still wrong — and check the href is *dialable*: `tel:<phone>` (spaces, no country code) is invalid in the URI scheme and silently fails to dial on some handsets and in-app webviews, where `tel:+447711080496` works everywhere. A malformed pattern in the shared header and footer puts it on every page, so report the occurrence count rather than the page you happened to find it on.

- **Fabricated testimonials on the reviews page are their own Critical, not a copy nit.** The page looks finished, so nobody re-reads it. Test every review for four missing signals at once: **no identity beyond a bare first-name-and-surname, no date, no star rating, and no link to a named review platform** (Google, AutoTrader). Then check the *vehicles* the reviews claim to have sold against live stock. On the a dealer rebuild all seven reviews were generic template copy — none dated, none attributed, no ratings — and four of the seven named cars were not in the 27-car inventory at all; one was attributed to a real, identifiable individual connected to the account, which removes any "these are anonymised" defence. Publishing invented consumer reviews is a practice specifically banned under the **Digital Markets, Competition and Consumers Act 2024** (fake-review provisions in force since April 2025) and a CAP Code breach on testimonials. It is a client/legal decision rather than a build ticket, but it is the finding to escalate first. Fix by deleting the section or replacing it with genuine verbatim reviews attributed to a named platform — paraphrasing real reviews is still fabrication. **And a machine translation is not a verbatim quote either.** Google serves review text in the *fetcher's* locale, so a Maps page pulled without a language parameter comes back with Google-translated reviews — fluent, plausible, and not the customer's words. Force the locale (`?hl=en-GB&gl=uk` on the place URL) and take the originals; where only a translated render is reachable, quote nothing rather than quoting the translation, because re-publishing a translation as a customer's own words is the same defect as inventing one. **Prefer internal-contradiction evidence over absence, because it is definitive and needs no profile read:** a body that duplicates another review's text verbatim under a different name, source or date, or one still carrying literal `[...]` placeholder brackets, cannot be a genuine verbatim review on its own terms. The sharpest version of that test costs one fetch — **read the site's own reviews page against the block you are judging.** A homepage carousel of testimonials beside a `/reviews` page reading *"No reviews yet. Be the first to leave one!"* is a contradiction the client cannot explain away, needs no external lookup, and is worth checking before anything else: a build that never seeded its reviews page is a build whose homepage review block was written by hand. Normalise and compare every review's body against the others, and grep each for `\[[^\]]+\]`, before going near the profile — on one build that caught both a placeholder review and a body reused word-for-word under a second reviewer's name, where the four-signal test alone would only have said "generic". **Confirm the absence against the whole review set before you call anything fabricated.** This escalation is only safe once the reviewer has been checked against the *full* listing — a capped or relevance-ordered view (Google's `search.google.com/local/reviews` returns 10, ordered by "most relevant") hides real reviews, and an absence counted there accuses a client of a banned practice on no evidence. Verify each name in the live signed-in profile, or ask Woody to look, before the finding leaves your notes.

- **Two Google Business Profiles for one business is a NAP finding, and it splits the reviews.** Query the review mirrors for the business *name* and the *postcode*, not just the domain — a garage trading as "Zagros Tyre and Auto Centre" had a second listing under "Zagros MOT Station and Auto Centre" at the adjacent street number. This changes the review count you cite when testing testimonials for authenticity.

- **Test every filter parameter independently — one working filter proves nothing about the others.** Each query param is its own code path, so a param that is simply never read still answers 200 with the *unfiltered* list. On a dealer `?make=BMW` correctly returned 1 of 1 and `?price_min=3000&price_max=4000` returned 3 of 3, while `?bodytype=MPV`, `?bodytype=Van`, `?bodytype=Estate`, `?bodytype=Hatchback`, `?bodytype=Saloon` and `?bodytype=SUV` each returned **all four cars**. Exercising one param and generalising reports the whole filter set as working. Probe each one and read the returned **ids and the "Showing N of M" count**, not the status. Then follow the category links that point at the broken ones: they are live, they carry a count in their own label, and clicking one contradicts the number that invited the click. Case is never the cause — `van`, `Van`, `HATCHBACK` and `bodyType=Van` all behave identically, so do not spend a pass on capitalisation. **Then check the count the page advertises, not only the cars it returns.** A listing heading can be a static, site-wide total that survives every filter: one build's heading read "90 vehicles for sale" on the unfiltered page, on `?make=Audi` (3 cars) and on the zero-result page directly above "Sorry, there were no search results". Compare the advertised figure against the result set on the filtered *and* the empty view, and check that each category tile's filter value exists in the filter's own dropdown — a homepage tile pointing at a body type the option list does not contain can never return a car. **Read the parameter's name *and* its accepted value set out of the form before testing either** — a guessed name, or a real name given a value the form never offers, returns a **zero-result page, not the unfiltered list** (`?price_max=10000` and `?pricerange=10000` both produced "no search results" where the form's real control was `pricerange` with range values like `0,10000`, which returned the full set). So "0 results" is ambiguous between an empty category and a bad parameter: pull the `<select name=…>` and its `<option value=…>` list out of the saved HTML and re-test with a value taken from it before either reading goes into a finding.

- **Client marketing claims are findings, not colour.** Stock-count, price-range, "award", "subject to status" and "protected by reCAPTCHA" statements must each be checked against the artifact that would falsify them (the listings, the script inventory, the form markup). Three of the template build's homepage claims were false. **Confirm a claim is not a deliberate feature before writing it up as false** — a live stock counter in the shared header, a site-wide total on a filtered listing, an intentional `noindex` each read as a miscount or a contradiction out of context and each is working as designed, so it is a judgement to put to Woody rather than an automatic defect. The tell is whether the same figure also appears where it *is* correct (the unfiltered view, the profile it counts): if it does, the real defect is usually the placement — a total sitting directly above a zero-result list — and the number itself is not the finding.

- **The same promise written twice, differently, is its own finding.** Warranty term, MOT term, service promise and delivery promise are typed into each page independently, so they drift. Grep every promise term across **all** saved HTML and compare. the template build's homepage and About Us promised "Minimum 6 months warranty … on every car over £5,000" while the warranty page said "3 Months Free dealer warranty on all cars" — two terms, two eligibility thresholds, two clicks apart. Severity High: a warranty term is a relied-upon consumer statement and the customer will quote whichever page suits them. Resolving it needs the client to confirm the real offer, so it belongs in the client bucket, not the build list. **Establish which wording is new** by fetching the outgoing site — the inherited line is there verbatim, and the version the old site never carried is this rebuild's invention.

- **A browse-by-X link block needs a coverage count, not just a link-health check.** A footer or nav block of make/model links can render perfectly — every link resolving to a real, populated page — while covering a fraction of the entities it exists to link, and a link-health sweep records that as a pass. One dealer's footer carried 14 make/model links spanning **three** makes (Audi, BMW, Citroën) while the site stocked **18**, and those 14 were the *only* `?make=` links anywhere on the site, so fifteen makes (Ford, Nissan, Volkswagen, Mercedes, Vauxhall …) had **no internal link at all**. Count the distinct entities linked **site-wide** against the full inventory — the stock search's own make/`<option>` list is the entity set — and confirm no other template carries the rest before calling the block complete. Report the shortfall as a coverage defect, not as broken links, and say whether the block is capped by design ("top N by stock") or hardcoded, because the fix differs.

- **A make-and-model H1 is informative; the client standard is transactional.** "Volkswagen T-Roc" names the car, "Volkswagen T-Roc for Sale in Bradford" names the car *and* the intent, and the transactional form is the default on **every** vehicle detail page and category page on every site we audit. It hides in two ways: the title tag often already carries "for sale" while the H1 does not, and a VDP title long enough (the template build's ran 114–149 characters) pushes "for sale" past the ~60-character SERP cut so it never renders. Check the H1, the title and the meta separately, and test a second `?make=` filter to prove the category template is not generic.

- **A fix applied by find-and-replace damages the copy around it — re-read the sentence, not just the string.** On a dealer, stripping the FCA status claims out of a live site left *"a dealer Motor Co Ltd is **an regulated** dealership"* on the homepage and the finance page (the article was not repaired), stranded lowercase *"**regulated finance**"* mid-sentence in seven places ("trusted by drivers for over 61 years. regulated finance, part exchange welcome"), and *"of **a** FCA-authorised firm"* on `/policies`. Three findings, one edit, and all of them live. After any term-level replacement, read every changed line in full — case, article and sentence have to survive — and grep the neighbouring words it could have orphaned ("a/an", capitalisation, a stranded adjective with its noun removed).

- **A claim removed in one phrasing survives in another — grep the concept, not the string.** The same pass deleted the footer's "authorised and regulated by the Financial Conduct Authority" and left **"FCA Registered"** as a homepage heading and an **"FCA Approved Dealership"** badge on `/about`. A competitor-facing status claim is stated several ways across a site; search for the *concept* (`FCA`, `approved`, `registered`, `regulated`, `appointed representative`) across every saved page, list what remains, and report the survivors as one finding. The same sweep should confirm the replacement statement is complete — a footer reading "credit broker, not a lender" beside an IAR line that never names its principal is still an incomplete disclosure, not a closed ticket.

- **A fix can create the obligation it was meant to satisfy.** Adding the stock feed published "11% APR representative" on every vehicle page — a regulated statement the pre-launch build never made, and which now requires a representative example that exists nowhere on the site. Pre-launch there was no APR anywhere, so a clean check. When a re-check confirms a build has *gained* a financial figure, a price claim, a rating or a certification, re-run the disclosure obligation that figure triggers rather than marking the area green.

- **An absence claim about company or FCA details must be measured across the page set, never the footer block alone.** A probe that read only `<footer>` reported "no dealer site shows an FCA firm reference number" across sixteen sites when **five** published one in full — three with both an FRN and a company number, one with an FRN only, and one authorised directly rather than as a credit broker — because the disclosure sat in the homepage copy, the finance block or a dedicated `/fca-disclosure.php`. **Read the count as provisional and count domains, not pages:** each widening of the path set found another compliant site, so publish the ratio beside the surfaces you actually probed rather than presenting it as final. Grep the rendered text of `/`, `/finance`, `/about`, `/fca-disclosure.php`, `/privacy-policy`, `/policies` and `/terms` for the *label* (`FCA`, `firm reference`, `FRN`, `company number`, `registered office`) and print matches with context, then report a ratio (`5 of 16 publish one`) rather than a zero. The sites that already comply are the wording model for the rest, so the finding becomes "copy this disclosure onto twelve sites" instead of an unactionable "nobody does it". **And a published FRN still needs checking** — a register mirror resolved one to the expected firm and returned individuals for two others, so list the numbers as published and put verification in the compliance pass; a wrong FRN is worse than a missing one.

- **A company name in a footer is a fact to look up, not a string to write.** An exact-name Companies House search returning no results means the trading name is not a company — do not let a footer invent `<Trading Name> Ltd`. Search the **postcode** on the advanced search instead: the registered entity is frequently a differently-named company at the same address with a used-car SIC code (45111/45190/45200), which is the candidate to put to the client for confirmation. Getting this wrong in either direction (inventing an entity, or printing none) is a Companies Act display-rule defect. Establish the **entity type** first: a sole trader has no company number, so close the finding as not applicable.

- **Extraction-tool mojibake is a false-positive trap** — `web_extract` and some crawlers return UTF-8 entities mis-decoded as Latin-1 (`weâ€™ve` for `we've`). Never log an encoding finding from an extraction alone: fetch the raw HTML with `curl` and confirm at byte level first. **The managed browser is a transport artefact in the same family:** it can decorate the page's own `document.title` (an emoji prefix was observed on a site whose served `<title>` was clean), so read the title, canonicals and every other head value from the served HTML, never from `js('document.title')` — when the two disagree, the difference is the harness, not the site.

- **Text you stripped out of the HTML is not necessarily visible on the page — strip `<!-- … -->` before you strip tags.** A tag-stripping regex (`re.sub(r'<[^>]+>', ' ', h)`) deletes tags but keeps the *contents* of comments, so a commented-out nav item, a disabled tracking tag and another dealership's name all land in the "visible text" and read as live defects. Two false findings came from one pass that way: a `-->` that appeared to render in the navigation (it was `<!-- <li class="ApplyOnline">…</li> -->`) and a rival dealer's name that looked like cross-client contamination (it was inside a commented-out finance address block). Strip comments first (`re.sub(r'<!--.*?-->', ' ', h, flags=re.S)`) and confirm the string's real state by grepping the **raw** markup for `<!--` within a couple of hundred characters of it. A wrong value found inside a comment is dead code — Low/Info — never a live contamination leak or a Critical; say which you found. Mirror rule for client-side templates: a `{{placeholder}}` in the served HTML is a Handlebars/JS template (confirm the library is loaded — `grep -c handlebars`), not an unfilled template variable to report as unrendered content.

- **The output pipeline redacts secret-shaped strings, so extracted code can look corrupted when the file is fine.** A JSON-LD block printed back as `{"@context":"https://***@type":"FAQPage",…` reads as mangled structured data and is a tempting Critical — but `grep -c '\*\*\*'` on the saved file returned **0** and `json.loads` parsed every block. Anything that looks like data corruption in *tool output* must be re-checked against the saved bytes before it becomes a finding (`python3 -c` on the file, not on the printed copy). Same family as the mojibake trap: the artefact is in the transport, not the site. **And the mask bites in the other direction when you are writing rather than reading.** A tool result prints a phone- or card-shaped string with its digits replaced (`tel:+447…` comes back with the middle digits as asterisks), and copying that line into a report or a client note puts the mask into the deliverable — where it reads as a redaction nobody asked for, or as if the site's own number were unprintable. Never type a numeric identifier from tool *output* into a document: take it from the source file or from a value you verified earlier, then `grep -c '\*\*\*\*'` the finished `.md` and re-check the rendered PDF before it goes out. The check costs one command and the failure is silent in exactly the direction that reaches the client.

- **A status-code sweep cannot see data-integrity bugs.** The highest-value checks on a dealer build are comparisons, not requests: md5 the response for `vehicle.php?id=<invalid>` against `stock.php` (a byte-identical body is a confirmed soft-404), count distinct vehicle ids per stock page against card slots and against the advertised count, and pull every listing price against the advertised price range. On the template build this found a soft-404, two duplicated stock rows, an inventory overstated by 20% and a "£3,000–£90,000" claim on stock that runs £5,995–£27,495. Full battery: `references/platform-data-integrity-checks.md`.

- **Derive the page set for any "N pages do X" claim from the crawled URL inventory, not from the templates you happened to fetch.** A title-tag sweep across six templates missed two bare-title pages on an 11-page site; the count reached the report, the developer message and the digest as 5 before it was corrected to 7. Recount by grepping the saved HTML of every inventory URL, and never conflate pages with templates — "11 static pages plus the VDP template" is not "15 templates". Numbers in a severity table are read as measurements, so an under-swept count is a credibility loss, not a rounding error.

- **A headline figure is duplicated across four artefacts — correct all of them in one pass.** Verdict counts ("9 Critical, 11 High, …") live in the working .md, in the report-builder script (cover block *and* the exec-summary list), in the digest, and in any client or developer message. After changing one, `grep -rn '<old string>' .` across the project folder rather than trusting memory; a delivered report whose cover contradicts its own severity table reads worse than the original miscount. **Grep to find, then judge each hit — a blanket sweep-update is wrong.** Any figure that moves over time (a review count, a stock total, an advertised price range) is **legitimately different** in every dated artefact: last month's report, a superseded audit and any historical snapshot were true when measured and must be left alone. The test is the artefact's measurement date against the figure's date, not whether the old string still appears — sweep only the documents describing the **current** state, and say in the handover which older ones you deliberately left. And remember editing the source does not touch the rendered PDF/DOCX/HTML: regenerate both and re-verify with their own parsers.

- **A finding you have to retract spreads further than a count does — and a retraction needs a visible correction notice, not a silent edit.** The same sweep applies, over more places: the working `.md`, every *rendered* artefact (editing the source does not touch the PDF/DOCX/HTML — regenerate them and re-verify with the format's own parser), `FINDINGS.md`, the digest, the copy already staged for delivery, and the skill whose pitfall taught the check. Add the correction where the wrong version appeared ("an earlier version of this record said X; that was wrong") rather than quietly overwriting it — the earlier copy may already have been read or sent, and the reader otherwise cannot tell which version they saw. **When the error was an assertion that something was absent, fix the method, not just the sentence** — see the fabricated-testimonials pitfall above.

- **Precompute a regex result before putting it in an f-string.** A Python f-string expression cannot contain a backslash before 3.12, so `print(f"{re.findall(r'\d+', s)}")` is a `SyntaxError`. In a multi-check probe script this fails one line at a time, costing a patch-and-rerun cycle per occurrence — assign to a variable first (`found = re.findall(...)`, then `print(f"{found}")`). Write the probe to a file and run it rather than pasting a heredoc, so a syntax error surfaces once instead of once per block.

- **Client-confirmed fixes may not survive a site rebuild or cache purge** — if a finding was "Fixed → verified" but later re-appears, it may be a deployment pipeline issue, not a regression in the fix itself. **The same distinction decides whether a feed fix holds: ask whether the repair was a data clean or a change to the import.** A record set scrubbed by hand reads green on every re-check until the next feed pull re-imports the same dirty source, so "0 of 59 affected today" is only a closed finding if the importer also decodes. Say which you verified, and put the question to the platform owner explicitly rather than reporting the repair as permanent.

- **Never record an identifier as present on a bare digit pattern — anchor it to its label and print the surrounding text.** A re-check sweeping for a company registration number with `\b\d{8}\b` reported one present on a site that carries no company number at all: stripping the tags concatenated adjacent text nodes in the review-rating widget and synthesised an eight-digit run from unrelated numbers. The finding was one line from going into the report as a *fix*, which is the worst direction for a false positive to travel — a fabricated pass is harder to catch later than a fabricated fault. Match label and value together (`company (?:registration )?no\.?\s*[:#]?\s*\d{8}`, `FCA (?:No|FRN)\.?\s*\d{6}`) and print the context around the match, not the match alone, before recording a positive. Same rule for VAT numbers, FRNs and phone numbers — and note that a bare-digits sweep is exactly what the FCA wording probe emits, so read its number columns as candidates to be qualified, never as findings.
