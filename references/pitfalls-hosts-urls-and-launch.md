# Pitfalls — hosts, URLs, launches and migrations

Split verbatim out of `dsc-website-qa` SKILL.md so the always-on rules stay readable. Each entry below is the original text in full; read the one you need when its title in the skill's Pitfalls index applies.

- **The staging subdomain is usually not the machine the site launches on.** On the platform builds `{dealer}.platform-host` resolves to the developer's own dev server, so a fetch can fail simply because that machine is off, and a stale canonical base or dev sitemap survives the copy to the live host while the domain does not. Re-verify on the live host after upload as its own pass, and record the launch IP when you are given it — see `references/domain-migration-and-ips-tags.md`.

- **Test whether the build is already on the live domain before accepting the brief's host labels.** A handover that calls one URL "staging" and another "the live site" sets the frame for every verdict that follows, and it can be stale in either direction: a build described as still awaiting launch was in fact already deployed, so the canonical/sitemap/indexability findings belonged to the dev mirror and *not* to the shipped build. Diff the two homepages (and one inner page) with the host names stamped out — if the only differences are the base-URL strings, both hosts are serving the same build:

  ```bash
  diff <(sed 's/staging\.example\.com/LIVE/g; s|http://|https://|g' stage.html) \
       <(sed 's/live\.example\.com/LIVE/g' live.html)
  ```

  Corroborate with the response headers (`server:`/`platform:`/`panel:`), the `robots.txt` `Sitemap:` line, which host answers `301` from `http://`, and whether `robots.txt`/`llms.txt` are **byte-identical** between the two hosts (a matching md5 is the same build). When the build turns out to be live already, the "launch blockers" re-classify as defects of the dev mirror alone and the report's framing changes with them — do not carry a pre-launch verdict onto a live site, and do not carry a live-site pass onto the launch host without re-testing it.

- **Build the redirect map against a fingerprint, never against a path prefix.** A blanket `/vehicle/*` rule redirects the live inventory, because the new build's own vehicle detail pages sit at that same prefix — the most obvious rule in the map is the one that breaks the site. Anchor every vehicle pattern to a token the OLD format always has and the new one never does (on these builds, a trailing UUID), and validate **both** directions: every archived URL caught, and **no live URL caught** — feed the live pages, the sitemap and a sample of current VDPs through the rule list and require zero matches. Direction one is a coverage report; direction two is the safety gate, and it is the one a spot-check never finds. Full procedure: `references/redirect-map-construction.md`.

- **Apache does not support inline comments after a directive, so a "helpful" annotation breaks the config.** `RewriteRule ^finance/?$ /finance.php [R=301,L]   # old /finance` parses the trailing words as extra arguments and the file fails to load, taking the site's whole rewrite behaviour with it. Put the note on its own `#` line above the rule, and validate the generated file in code — four tokens per `RewriteRule` line, flags matching `\[[A-Za-z0-9=,;]+\]`, balanced parens, zero `#` on any rule line.

- **A partially-working redirect set has two readings, and only probing by URL SHAPE tells them apart.** Two legacy URLs resolving correctly (`/contact-us`, `/stock/used-cars-in-holmfirth` → 200) beside 59 that 404 turns "no redirects in place" from an architecture complaint into a specific, actionable ticket — the mechanism demonstrably exists and the map is simply incomplete. The opposite pattern means something different again: one rebuild redirected **all 13** keyworded `/stock/…` landing pages to the correct filters while every extensionless static page (`/finance`, `/contact-us`, `/about-us`, `/warranty`) 404'd against the `.php` equivalent the new build actually serves — a map written for the pages the developer thought of, not for the site. Adding an extension to a path family is enough to orphan every old URL in it, so probe **one URL from each family** (landing pages, static pages, vehicle detail in every slug form the old site used) and report coverage per family. A spot check that lands on the working family records the whole map as done, and the loss lands in the coverage report a fortnight later.

- **`/readme.md`, `/llms.txt` and the build's own docs directory are worth a direct probe.** The newest the platform generation ships a real `/llms.txt` (a genuine pass — record it) and can ship its developer `README.md` at the web root answering 200, naming the platform, the stock API integration and the complete internal file map. It is rarely in the `robots.txt` `Disallow:` list, so the standard Disallow-probe sweep misses it — request it explicitly alongside `package.json` and `composer.json`.

- **Crawl the outgoing site the same day, before reporting a regression.** It is the only way to tell "lost in the rebuild" from "never existed" — and it yields the redirect map for free, since a dealer's old `sitemap.xml` is frequently a soft-404 with no usable URL list. Once it *has* gone, the Wayback CDX index replaces the crawl as the URL source and reaches URL generations the crawl never could — see `references/redirect-map-construction.md` §1.

- **A sitemap can live at a non-standard path, so probe several before reporting "no sitemap" — then read what it actually lists.** `/sitemap.xml` and `/sitemap_index.xml` both returned 404 on one build while the real index sat at `/sitemap-index.xml`, pointing to `sitemap-pages.xml` and `sitemap-vehicles.xml`. Once found, compare the pages sitemap against the live page inventory (it omitted a live orphaned About page and a linked apply page) and against the `noindex` set (it *included* a page serving `NoIndex Follow` — a self-contradiction, not a pass). Also check the vehicle sitemap count against the advertised stock figure: a match there is a genuine pass worth recording.

- **A served sitemap can be a static snapshot with the generator sitting unused, and a malformed URL hides the difference between "wrongly written" and "dead".** Read `<lastmod>` on every entry: one identical date across all of them is the age of the *file*, not of the stock. Check which path serves what — a `RewriteRule ^sitemap$ sitemap.php` regenerates only on the extension-less form, so `/sitemap.xml` keeps hitting the last-written file and nothing refreshes it; the rewrite has to cover `^sitemap\.xml$` as well. Then test every loc **twice**, as written and with the malformation corrected (`//car/` → `/car/`): entries that 200 only in the corrected form are a formatting bug (a `$baseUrl` ending in `/` concatenated with a `getCarUrl()` that returns a leading `/`), entries that 404 in *both* are sold stock never pruned, and the two need separate counts because only one is a code fix. Report the split rather than a single "N dead links" — a reader cannot tell what to fix otherwise.

- **When a defect is in the shared template, count the estate before writing it up — and check whether the site's own header is what makes every slug canonical.** (a) Run the same probe across every dealer site you can enumerate and report the ratio ("7 of 14 serve the homepage as `robots.txt` and return 200 for unknown paths"), because that decides whether it goes to the platform owner as one ticket or to the client as theirs; a template defect named against one dealer gets fixed seven times or not at all. **Enumerate the population from the host's own file tree before you run the probe** — the FTP listing, the four buckets (dealer site / directory network / platform / other), the alias pairs counted once, and the defect matrix to report: `references/dealer-estate-inventory.md`. **Then re-probe the sibling sites for the fix itself** — the repair is applied *per site at launch*, not rolled out, so a build regenerated on its go-live day is clean while a sibling that launched earlier still serves the dev file. Fetch the same path across the estate and report the split ("fixed on three, still live on two"), because "the platform is broken" is disputable when most sites are fine, whereas "this deploy step was missed on these two" is a job someone can take today. (b) On the platform builds `car.php` looks a vehicle up by **id alone** and ignores the slug, while `includes/header.php` builds the canonical from `REQUEST_URI` — so `/car/<id>/anything` returns 200 and declares *itself* canonical, giving every car unlimited self-canonicalising URLs. Prove it with one fetch of a deliberately wrong slug. Then sequence the fixes: regenerating the sitemap re-slugs cars from current feed fields and therefore puts a *second* live URL per car online, so the canonical ships before the sitemap.

- **Probe the exposure surface on every new build before writing the page-by-page findings.** A *real* `robots.txt` is not a pass on its own: its `Disallow:` list is the template's own inventory of development and debug files (`test.php`, `stock-debug.php`, `gencars.php`, `debug-rewrite.php`, `content.json`, `package.json`, `/admin.php`), and on the platform builds those sit publicly at the site root answering **200**. Treat every `Disallow:` entry as a filename that exists, status-check the list, and read what the 200s expose — debug pages leak the absolute server path, the stock API endpoint and the dealer ID, and a generator endpoint can be a live **write**. Never trust `robots.txt` advertising a path as evidence it is protected; listing it invites the request. This is frequently the highest-severity cluster on a build whose SEO head-layer is otherwise correct, so it can change the report's headline. Worked example and the path table: `references/platform-audit-patterns.md`.

- **A go-live date passing is not evidence the cutover happened, and the DNS can move under you mid-session.** Check the staging host and the live domain as two separate facts before writing up a post-launch re-check. On one build the live domain was still serving the outgoing developer's site (so every "fixed" verdict was measured against a host no customer was seeing), and within the same session the live domain then lost its DNS records altogether — a state that cannot be described from a fetch taken earlier in the turn. Re-confirm resolution at write-up time, take the report's date from `date` rather than reading it out of session context, and state which host each verdict was verified against.

- **A pre-launch check inherits two false assumptions: that staging is reachable, and that the launch host has the build.** (1) A dev box can be alive and closed to you — every vhost returning the same Apache 403 on every path is an IP allowlist, not a broken site, so probe two or three siblings before writing one site up as down, and label inherited findings "as at the capture date, not re-verified". (2) A launch host may have no vhost at all: `curl -H "Host: <domain>" http://<ip>/` returning 403 plus a TLS failure on that SNI means DNS cutover would be a hard outage, so sign off on the build being present on the launch IP, not on the dev box.

- **You cannot diff a PHP file over HTTP — the request executes it, so every file looks months out of date.** `curl https://site/index.php` returns the rendered HTML, and comparing that against the repo's `index.php` reports 7.8 KB on disk against 23 KB "live" for a file that is byte-identical, while `functions.php` comes back at 0 bytes because it only defines functions. Fetch the **source** into a scratch directory and diff that, then confirm the checkout is on the branch you think: a working tree sitting on someone else's fix branch makes unrelated folders read as modified. On these Hostinger boxes the reliable fetch is Python `ftplib` — `FTP_TLS(host)`, `login(...)`, `prot_p()`, then `retrbinary("RETR <path>", ...)` with `cwd('/domains/<domain>/public_html')` — which resolves the docroot paths that curl's FTP URL form refuses outright.

- **Check whether every outbound CTA destination still exists — including off-site ones.** A dealer's booking subdomain or tyre site can lapse, be renamed, or never resolve, while the live site keeps 13+ links pointing at it. `dig +short <host> @1.1.1.1` returning nothing (`NXDOMAIN`) plus an RDAP 404 confirms the domain is gone rather than merely unresponsive, which is a Critical conversion failure and not a broken-link nit. **A CTA rendering `href="#"` is a different fault again: the widget has no `link` setting at all, not a lapsed one.** A scan for empty or `#` URLs in `_elementor_data` returns nothing and reads as "no dead links" — detect it in the rendered markup instead, and fix it in the data. Both shapes exist on one site; probe for them separately.

- **Never extract internal links with `href="/`** — builds vary between root-relative (`/about.php`), extension-less (`/about`) and bare relative (`about.php`) links, sometimes within one platform, and the anchored regex returns zero paths and reads as "no internal links" rather than "bad pattern". Match all `href="..."`, filter assets by extension, then prepend `/` to bare relative paths before status-checking them.
