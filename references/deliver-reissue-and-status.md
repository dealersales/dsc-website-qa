# Delivering the QA report — reissue, status and ownership

Split verbatim out of `dsc-website-qa` SKILL.md §5 so the delivery rules stay readable. Each paragraph is the original text in full.

**Once fixes start landing, the report becomes a status board — `references/audit-status-tracking.md`** covers the owner→status re-cut, the standing "nothing is deployed" statement, and the redacted-value trap that puts a masked phone number in a client document.

**Re-verify before re-dating, and leave one copy of the client report on disk.** When the report is reissued under a new date, re-run the checks the same day and confirm each retained finding still reproduces live before the new date goes on the cover — a re-dated report asserting a week-old fact is worse than the original. **Re-run the headline measurement immediately before you render, not only when re-dating:** the defect a dealer is complaining about can be fixed between your passes, so a figure measured one afternoon can be obsolete the next morning and the document then states a fault that no longer exists — which is worse than a low number, because it hands the reader a reason to distrust everything else in it. Re-measure, date the cover with the time as well as the day, and say in the body that the item has since been repaired if it has. Then delete the superseded version everywhere it exists: the source `.md`, the rendered PDF/DOCX/HTML, and the staged copy in the delivery cache, so the stale one cannot be sent.

**When the fixes are already built at reissue time, the fix list becomes a status board and the findings stay written as found.** Woody asks for this directly ("update the audit to reflect all the fixes we can do"), and the temptation is to rewrite the findings as fixed — don't: production has not changed, and a reader sent a document claiming otherwise checks the site and finds it broken. Three edits and no more. Put a one-line **Status:** at the top of each finding whose fix now exists ("fixed in `<branch>`, not deployed"), so the finding still describes the live site. Add a standing sentence under the summary: nothing here is live yet, every finding was re-checked at a stated time and still reproduces, and what has changed is *ownership* — the work is written, committed and verified, and is waiting on a deployment decision rather than on a developer. Rebuild section 7 as three tables — **Done** (item · fixes · the assertion that proved it), **Still to do** (and why it is not in the patch), **The dealer's** (and why it cannot be ours) — because the reader's question has changed from "what is wrong" to "what is left". Carry the same edit into the cover verdict: a cover reading "5 Critical" beside a body saying twelve are built is a contradiction the reader resolves against you.

**When a deadline is attached, close with the one-upload subset.** If the client needs it live by a named day, add a short paragraph naming the items that change what a customer can do and ship together (the enquiry form, the menu, the 404s, the sitemap), the single item blocked on the client's word, and what to do if that word does not arrive in time — take the unsupported claim off the page rather than leave it up. That paragraph is what turns a status board into a decision, and without it the document is read, admired and set aside.

**When the site is already live, the framing changes.** The section-2 heading is not "make a launch unsafe" but "these are live and can't wait", and its contents are compliance, reputation and data-integrity defects rather than launch blockers — a fabricated reviews section, two contradictory APRs, another dealer's inventory in the live sitemap. There is no "Before go-live" section to write; items 3–5 collapse into a single priority-ordered list. Keep the go-live framing for pre-launch staging batches only.

**Anchor every deadline to a date, never to a relative count.** A handover is written once and
sent days later, so "nine days out" or "go-live is in a week" is already wrong by the time the
developer reads it — and it makes the author look careless on a document whose whole value is
precision. Write "with go-live on 30 September" instead. The same rule applies to "today" and
"this week" in anything client-facing that may sit before it is sent. The audit's own header is
the exception and can stay anchored to its audit date ("9 days from this audit"), because there
the anchor is explicit — but a message in present tense has no such defence.

Two rules that make it land. **Label the owner on every item** (Build / Feed / Client / Server / Client + compliance) so the developer can triage without asking. And **give the fix, not just the diagnosis** — the reader is technical, so name the tag, the header and the config flag. Where the client's outgoing site already does it correctly off the same feed, say so: it is the strongest available argument for the change.

**Before labelling an item "Build (the platform owner)" — or naming any platform owner — establish that the file is out of our reach.** Woody pushes back on work parked with the platform owner when we could have done it ourselves, and the reply that follows is "are any of these something we can do?", which turns a finished audit into a second pass. On the platform estate we hold FTP to every dealer docroot, so most of what a first draft assigns to the builder is ours: the template patch, the 404 guard, the sitemap generator, `robots.txt`, the canonical, the forms, the footer legal block. The test is not whose *code* it is, it is whether the change lives in a file we can edit. Reserve the platform bucket for the stock feed and platform database (per-record `finance`/APR values, lead routing), and say in the item *what* in it is unreachable. Two things still gate us even when the file is ours: dealer sites need Woody's explicit go-ahead (he clears it with the platform owner), and the client's compliance wording is never ours to author. So the split is three-way — **ours to do now / the platform's / the dealer's decision** — and "ours" should be the largest column, not the one saved for last. **Establish the access before the first draft, not after Woody asks:** the credential in the keychain, an FTP/SFTP listing of the docroot, and a source-level diff proving the repo matches the live files are three checks that decide the whole table, and each of them is cheap. What stays in the platform bucket is what lives outside the docroot — the stock feed and its per-record `finance`/APR values, lead routing, the shared API — and the item should say so explicitly rather than naming a person.
