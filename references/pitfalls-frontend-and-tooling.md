# Pitfalls — front-end behaviour and tooling

Split verbatim out of `dsc-website-qa` SKILL.md so the always-on rules stay readable. Each entry below is the original text in full; read the one you need when its title in the skill's Pitfalls index applies.

- **React hamburger menus are notoriously unresponsive to synthetic clicks** — always try the `<style>` injection workaround before concluding a menu is broken. If the menu still doesn't appear, note it as "inaccessible via automated testing — requires manual check." But make the *detection* trustworthy first, because a probe that finds nothing is indistinguishable from a site that has nothing. A scan for class names (`hamburger`, `nav-toggle`, `mobile-menu`) or a `button` listing returns empty on a toggle that is a plain `<button onclick="toggleMobileNav()">` containing only an SVG and a Tailwind class like `hidden lg:inline-flex` — and an evaluate expression with a syntax error returns `null` just as silently. On one the platform build that sequence read as "zero nav links visible, no hamburger", i.e. a Critical mobile failure, while the toggle existed and worked. Before writing any "no mobile navigation" finding: dump `document.querySelector('header').outerHTML` and read it, click the toggle, and confirm by reading the target element's computed `display` and offset height **before and after** rather than judging whether the menu looked open. Also do not assume the `<style>` workaround is needed — a plain-JS toggle responds to a synthetic `.click()` fine. That same build closed as a pass plus a Low accessibility finding (40×40 px toggle, no `aria-label`/`aria-expanded`/`aria-controls`).

- **Before reporting a mobile menu as broken, check whether the toggle is bound TWICE.** A plain `<span class="mobile-toggle" onclick="document.querySelector('.nav').classList.toggle('open')">` plus a JS listener with the *same body* fires twice per tap: the class goes on and straight back off, so the menu never opens and nothing errors. It reads exactly like a dead handler and defeats every "did the click land?" probe, because the click does land — twice. Diagnose by patching `DOMTokenList.prototype.toggle` to log `(this.value, arg, this.contains(arg))` and then issuing one real click: the log shows `nav | toggle(open) -> false` immediately followed by `nav open | toggle(open) -> true`. Confirm the CSS is innocent in the same pass by forcing the class (`nav.classList.add('open')`) and measuring — if the menu then opens, the CSS and the handler are both fine and the duplicate binding is the whole defect. Also enumerate the bindings: `cdp('Runtime.evaluate', expression="getEventListeners(document.querySelector('.mobile-toggle')).click.length", includeCommandLineAPI=True)` — one more `click` listener than you added means a duplicate.

- **A measurement can be correct and still target the wrong element, or the wrong moment — two false Criticals in one pass.** (1) A mobile nav reported as not opening: the reveal rule targets the panel itself (`#hamburger-input:checked + label #sidebar-menu { visibility: visible; right: 0 }`), while a wrapper *inside* it measures height `0` whether or not the panel is open — measure the element the selector actually names, then settle any contradiction between `getComputedStyle` and what is on screen with a screenshot after a real click (`click_at_xy`, or `Input.dispatchMouseEvent`), because the computed value can be the pre-transition one. (2) Stock images reported as broken: `naturalWidth === 0` is the normal state of a `loading="lazy"` image that has not entered the viewport. Scroll the page, wait, and re-count; if any still read 0, load each URL in a fresh `new Image()` and read `onload`/`naturalWidth` before writing the finding.

- **Check what the CSS framework is, not just the head tags.** A production build can be loading a *development* stylesheet engine. Grep the saved HTML for `tailwindcss`, `cdn.`, `unpkg`, `jsdelivr` and the stylesheet basename before recording a performance verdict; Tailwind's Play CDN (`https://cdn.tailwindcss.com`) in particular is dev-only, render-blocking, and leaves the site unstyled if the third party is unreachable. Build-layer defect: it belongs in the developer handover, not the client list.

- **A form's markup in the page source proves nothing — count `<form>` elements in the rendered DOM.** Elementor/MetForm widgets mount client-side and fail silently at `height: 0`, leaving the plugin's template script and an empty mount point behind. A page whose entire purpose is the enquiry form can ship with the form simply absent, and no console error will say so. See `references/first-pass-discovery-battery.md` §10.

- **A modal that opens blank is usually a framing header, not a broken endpoint.** A vehicle enquiry CTA that iframes a platform route (`<platform-host>/tracking/enquiry-form?car_id=…`) opens an empty panel when the framed URL answers `X-Frame-Options: SAMEORIGIN` — the browser refuses a cross-origin frame and paints nothing, with no error the dealer will ever see. `curl -sI` the iframe's own `src` and read the header *before* concluding anything about the form: fetch it directly and you will find a healthy 200 and a complete form, which is what makes this so easy to misreport. The fix belongs on the framed host (`Content-Security-Policy: frame-ancestors`, or a route-scoped wildcard), never on the embedding site — and where the endpoint is shared across a dealer network, check whether every other dealer's form is dead too before writing it up as one client's bug.

- **Count `<form>` elements on the page the CTA actually points at, not on the site.** A build can ship six working forms and still have none on the two pages that matter, and a "does the site take enquiries" check answers yes. On a dealer `contact.php` and `sell.php` contained **zero** `<form>` tags — the contact page offered only `tel:`, `mailto:` and WhatsApp — while every vehicle page's **Make Enquiry** button linked to `contact.php?vehicle=…` and landed on that page, discarding the vehicle parameter on the way through. The tell is to follow the CTA rather than reading the nav: fetch each page the enquiry/booking/valuation button targets and grep it for `<form`. A page that looks complete because it is full of contact details is the failure mode here, and the same check catches the mirror case — the page that *does* have the form (`sell-your-car.php` on that build) sitting outside the menu and the sitemap while the menu links to the empty one.

- **URL migrations leave stale URLs in two places** — stored data (fix with `wp search-replace`, searching on the **bare host** because Elementor escapes slashes as `\/`) *and* the Elementor element cache (`_elementor_element_cache` postmeta), which search-replace cannot touch and which keeps serving the old URL in the rendered page. Symptom: front end shows the old URL while both the stored Elementor data and `wp_get_attachment_url()` return the new one. Full procedure: `references/url-migration-and-elementor-cache.md`.

- **Never open the Elementor editor on a live client site to change one value.** The editor boots the whole builder and loads the entire `_elementor_data` payload into memory; on a memory-tight host with a large payload that can 500 the site outright — frontend and wp-admin both — and the access you would use to fix it goes with it. A single string (email address, phone number, label) goes in via WP-CLI/SSH or the host's SQL tool — and via in-session REST only where that meta key is *exposed* to REST, verified by read-back, because an unregistered-key write returns 200 and changes nothing (`references/applying-fixes-via-in-session-rest.md`). It also must not be probe-tested with a placeholder payload: where the key *is* registered that write succeeds and destroys the page's design. And `_elementor_data` is snapshotted *before* the post is touched, including before an editor visit that exists only to regenerate compiled CSS. Mechanics and destroyed-payload recovery (revisions still hold their own `_elementor_data`, so a
wrecked page is recoverable without a snapshot): `references/applying-fixes-via-in-session-rest.md`;
site-down triage: `references/site-down-triage.md`.

- **SiteGround Optimizer's combined CSS bundles carry absolute URLs, so a staging host outlives the migration.** `grep -c 'sg-host.com'` on each `siteground-optimizer-assets/*.css` bundle is a five-second check that catches the whole class — Elementor's Google Fonts cache is the usual carrier, the symptom is every webfont failing and the site rendering in fallback system fonts, and the fix is Elementor → Regenerate CSS & Data followed by a cache purge. See `references/first-pass-discovery-battery.md` §11.

- **Match HTML attributes quote-agnostically — WordPress and Elementor print single-quoted attributes, so a double-quoted grep returns a false negative.** `<meta name='robots' content='noindex, nofollow' />` is what WordPress actually emits, so a check written as `name="robots"` finds nothing and reports the fix as *not applied*. It is the mirror of the bare-digit trap above and just as hard to catch, because a reported failure invites no scrutiny at all. Anchor on the tag name loosely (`<meta[^>]+robots[^>]*>`) and assert on the **value**. Pair it with a fresh server-side fetch — a third-party render service or the host's edge cache will hand you a pre-change page and manufacture the same false negative from the other side, so purge as part of the write rather than after it.

- **Distinguish a UA-specific crawler block from rate limiting by testing several UAs inside the same minute.** `GPTBot` returned **429** on three attempts with a 20-second gap while `curl`, `PerplexityBot`, `ClaudeBot`, `OAI-SearchBot`, `CCBot`, `Bytespider`, `DuckDuckBot` and `YandexBot` all returned 200 on the same page — that pattern is a host rule against one bot, not a throttle, and it is the only cheap way to tell them apart. Conversely **a 403 to a `Googlebot` or `bingbot` user-agent from a different IP proves nothing about crawl access**: managed hosts (Hostinger, SiteGround) refuse unverified spoofed bot UAs by design, so report it as "unverifiable from here — confirm in Search Console", never as "Google is blocked". Do not report the AI-crawler position without the robots.txt to match: no robots.txt means no stated policy, so the block is an accident of the host config rather than a decision anyone made.

- **Never trust a single failed status code** — bare `curl` User-Agents get 403 from bot-blocked hosts (SiteGround/Wordfence). Re-test with a browser UA before reporting a page as broken or blocked. **And never trust a sweep whose results are uniform** — 36 identical `200`s from a proxy is a wall, not a site. Guard on a positive assertion (a title present AND a body above a length floor), because a check written against the one challenge you already know will score a *different* vendor's interstitial as success: an `sgcaptcha` guard let Cloudflare's `Just a moment…` through as `200` with zero bytes of content, and a false pass is harder to catch later than a false fault. **A path that fails while an equally-random sibling path of the same type 404s proves the file exists and is being *refused*, not missing** — a `403` on `/robots.txt` beside a `404` on `randomfile-xyz.txt` means robots.txt is there and the request is refused at the edge (observed on a Cloudflare-fronted host, where `.txt` and `.php` paths were refused while page paths and `.xml` files served `200`). That distinction changes the finding: "robots.txt is missing" is a defect anyone can fix, whereas "robots.txt exists and refuses automated fetches" is a per-path WAF/edge rule to be verified from Search Console — never report such a file as absent. **A total connection failure is the same trap from the other direction:** this machine egresses through a VPN (Hydra Communications, AS25369) and some hosts answer nothing to that range — TCP connects on 80/443 and then the request dies (`000`, `Empty reply from server`, `SSL_ERROR_SYSCALL`). dealer-site.co.uk was reported as broken this way; it was serving the whole time and the client confirmed it on his phone. Identical DNS answers from the system resolver, 1.1.1.1 and 8.8.8.8 rule out a resolution problem but prove nothing about the path. Before writing any "site is down" or "domain dead" finding, re-fetch from an independent vantage point (`curl -s -m 45 "https://r.jina.ai/https://DOMAIN/" | head -6`) and check for `NXDOMAIN`. **But a perfect DNS answer does not clear the domain** — a name can resolve cleanly to a machine that is gone, which is a hosting outage and needs a different fix entirely. Read `connect` as well as the status code: `http=000` with `connect=0.000000s` on every port (80, 443 and the mail ports) means a dead host, not a slow site. Only a dead DNS answer plus an RDAP 404 justifies a *lapsed*-domain claim. And treat an `r.jina.ai` `TimeoutError … networkidle` as inconclusive either way — it also fires on a healthy page running a long-polling script, so it corroborates a direct TCP test but never replaces one.

- **Never `pkill -f "Google Chrome"` — it kills the Hermes-managed browser.** Its CDP browser runs from `--user-data-dir=~/.hermes/chrome-profile` on a fixed debugging port, so a broad pattern takes out the session doing the work. Kill by PID from `pgrep -fl`, or scope the pattern to a scratch `--user-data-dir`. Rendering and blocked-site evidence pitfalls: `references/rendering-and-access-pitfalls.md`.

- **Check that every published email address can actually receive mail.** `dig +short MX <domain>` and `+short TXT` returning nothing means the `info@` address in the header, footer, contact page and JSON-LD `email` field is dead — silently, at both ends, on a site whose whole purpose is enquiries. Rate it Critical rather than a copy nit: the customer believes they made contact and the dealer never learns otherwise. Same family as the lapsed-CTA-destination pitfall, and the fix is a mailbox plus MX/SPF/DKIM/DMARC or a different address, decided **before** the domain moves.

- **Probe the rendered PDF with `unicodedata.normalize("NFKC", …)` or a text check reports a fix as missing.** Montserrat headings in the house renderer emit ligature glyphs — `ﬁve`, `ﬁnance`, `ﬁle` all come out of `extract_text()` as U+FB01 — so a plain `"five sites carry" in pdf_text` probe returns False against a document that is visibly correct, and a re-check of a delivered fix reads as still open. Normalise before every string assertion, and keep the same rule for `.docx` where a heading run can inherit the ligature too.

- **Prove the access before you promise the fix.** "We can do this ourselves" is a claim about four things, and each takes one command: the credential exists (`security find-generic-password -s <item> >/dev/null`), the session lists and retrieves the live docroot, the repo matches production for the files you are about to touch (source diff, above), and there is a local PHP to `php -l` the result (`~/.local/php-static/php`). Say which of the four you checked — an audit that hands work back to a platform owner it could have done itself costs a second pass, and one that promises an upload it cannot make costs the client's trust.

- **Look at the page you just patched, even when it is only on a local server.** A local build is not reachable from the agent browser (it refuses private addresses), so verify visually by making the page self-contained: fetch it from `php -S`, replace the `<link rel="stylesheet" href="css/style.css">` with an inline `<style>` of the same CSS, rewrite `src="images/` to absolute URLs, then `qlmanage -t -s 1200 -o /tmp/q /tmp/page.html`. That caught an unstyled submit button on a form that every textual check had passed. Two expectations to set: a broken-image marker in the thumbnail can just be Quick Look declining to fetch an asset that returns 200 to curl, and a headless `--screenshot` of a page pulling Google Fonts and a CDN stylesheet can sit past its timeout — wrap it in `perl -e 'alarm …'` and fall back to `qlmanage` rather than concluding the page is broken.

- **`sips` renders a Chrome PDF's transparent page background as black, so a correct report looks like an illegible dark-mode failure.** Chrome's `--print-to-pdf` leaves the page background transparent; the banner blocks are opaque and render fine, so a cover check reads as "branded and broken" — dark text on black, headings barely visible — while the PDF is perfectly good in every real viewer. Confirm the artefact with a different rasteriser before changing any CSS: `qlmanage -t -s 1000 -o /tmp/ql report.pdf` produces a thumbnail that composites onto white, exactly as Preview and Acrobat do. Two related render traps in the same call: verify the PDF is actually **current** (`md5` twice, and check the mtime against the clock) because a headless Chrome launched against a profile that is already running hands the request to that instance and writes nothing while the script reports the old file as written; and never conclude "the render is broken" from an image the same toolchain produced.
